## A1：租户隔离

**要求。** Bob 只能访问 West；列表、详情、批量发证和导出都必须隔离。跨租户详情不可泄露记录存在性，跨租户发证不能有副作用。

**设计。** `actor()` 从 header token 查出管理员与 tenant。业务函数使用该 tenant，不信任客户端传入的 tenant_id。列表和导出共用 `query_spec()` 的租户条件；详情、撤销、课程都单独限定 tenant。批量发证先校验课程归属，再进入幂等查询。复合外键进一步阻止租户和课程、学员、审计错配。

代码入口：[app/main.py](../app/main.py) 的 `actor/query_spec/detail/bulk_issue/revoke`；数据库约束见 [app/db.py](../app/db.py)。UI 用 `Console key={token}` 在切换身份时重建界面，并取消旧请求。

**已验证。** 双向越权、伪造 tenant_id、跨租户 serial 搜索、空导出、课程列表范围、缺失/错误 token；跨租户详情与不存在详情的状态码及正文一致；非法写入前后 certificates/audits/operations 数量不变。双方发证后搜索同名 Alex，只出现各自数据。Chrome 原实测包含延迟 East 响应期间切 West。本次额外确认：已使用 key 换成越权课程，仍先返回 404，不泄露先前操作结果。

**完备性。** 题目指定入口及双向隔离覆盖较强。公开的 `/api/actors` 是题目允许的演示身份选择，不能将其解释为生产身份认证。非法 token 在每一个业务路由上的排列组合没有逐一测试，但这些路由都使用同一个 Actor dependency。

## A2：顺序重试、并发重试

**要求。** 同 actor、同 key、同请求只有一个逻辑操作；每位符合条件的学员至多一张证书，每次实际发证恰好一条审计，重复调用得到同一份结果。

**设计。** 浏览器创建 UUID，保留到结果确认；服务器不临时替换 key。`operations` 持久化规范化请求和完整结果，以 `(tenant_id, actor_id, kind, idempotency_key)` 唯一。`BEGIN IMMEDIATE` 先取得 SQLite 写锁，随后查询/创建操作。

两个同 key 请求同时到达时，第一个先执行；第二个等待写锁。第一个提交后，第二个读到已经提交的 result_json，直接重放，不再次执行学员循环。证书、ISSUED 审计、操作结果在同一外层事务中提交；回滚时也一起撤回。数据库另有证书业务唯一约束和审计唯一约束，覆盖不同 key 造成的业务重复。

**已验证。** 顺序重试、重启后重试、5 路同步并发同 key、5 路不同 key 操作同一课程、另一租户复用同字符串 key。断言不止是成功响应，而是完整 JSON 相等、操作数和证书/审计增量准确、每张证书恰好一个 ISSUED 事件。Chrome 验证过双击、禁用按钮、提交已成功但响应被代理丢弃后用原 key 重试。补测两独立服务进程、6 路并发同 key：全部返回相同结果，增量 `(2,2,1)`。

**已确认的边界。** 写锁等待设置为 15 秒，锁持续被占用时返回 503。补测约 16.43 秒后得到 503，数据库无副作用；释放锁后原 key 重试返回 200，并只产生正常的一份副作用。安全性成立，但“所有调用直接获得同一操作结果”不是无限等待保证。即使重放已完成的 key，当前代码也先申请写锁，可能被无关写事务阻塞。这是 A2 在更严格压力/长耗时检查下的风险。

此外，前端 pending key 只在组件内存中，页面刷新或切换 actor 后不保留。数据库仍能阻止重复证书，但用户可能发起新操作并看到 skipped，不能自动恢复原操作的 issued 结果。此点由源码确认，未补做刷新故障 UI 实测。

**完备性。** 并发去重、持久化重放和提交后丢响应覆盖较强。未在提交瞬间杀进程、模拟磁盘损坏，未测大量长期等待者；不能用现有小规模并发测试声称任意负载均可用。

## A3：幂等键误用

**要求。** 同 key 对不同课程/有效 payload 必须返回 409，不能执行新操作或覆盖原结果。

**设计。** Pydantic 限定请求为严格整数 course_id，拒绝额外字段；通过校验后，规范化 JSON 保存为 request_json。同一作用域的 key 已存在时，先比较规范化内容。语义相同的空白变化仍是重试，课程变化则冲突。未知字段属于无效请求，返回 422，不进入业务执行。

**已验证。** 101 成功后同 key 发 102 返回 409；全部计数和原 operation 行不变；再发 101 仍返回原结果。两门课程竞争同一个 key 时恰好一个 200、一个 409，败方课程证书数不变。JSON 空白差异、额外字段和缺失 key 均已检查。越权课程优先 404，避免通过 key 重放绕过授权。

**完备性。** 当前有效业务 payload 只有 course_id，已覆盖其主要语义变化。没有多个业务字段可供排列组合；以后增加字段时需要重新审查规范化和冲突判定。非法类型、空白 key、超长 key 等校验并未逐项覆盖到测试。

## A4：逐学员结果与发证审计

**要求。** 完成且尚未获证才发证；未完成、已经获证明确 skipped，返回 issued/skipped/failed 的逐人结果。

**设计。** 按 learner_id 遍历报名，查询已有证书和完成状态。每次实际发证在一个 savepoint 中同时插入证书和 ISSUED 审计。可恢复的 IntegrityError 会回滚该学员的两项写入并记为 failed；其他学员可以继续。最终所有结果在外层事务提交。非局部数据库错误可以让整个请求回滚并返回 503。

这意味着审计失败时，不会留下“已发证却无审计”的半成品；重试同 key 也不是把成功项再做一遍，而是读已保存的原结果。已记录为 failed 的项，同 key 仍返回原失败；使用新 key 才会尝试新的业务操作。

**已验证。** 正常结果为 Alex/Morgan issued、Jamie not_completed、Casey already_certified。数据库触发器故意拒绝 Morgan 的审计：Alex 成功，Morgan 的证书与审计都不存在，逐项结果及 summary 精确匹配。去掉故障后，同 key 仍返回原失败，新 key 可补发 Morgan。另一个触发器拒绝保存最终 result_json：整批证书、审计、操作全部回滚。补测空课程得到空 outcomes、全零 summary，只有一条操作记录。

**完备性。** 正常资格分类、局部失败、整批失败和副作用对齐覆盖较强。全部未完成、超大课程报名量等组合未单独做性能测试。业务选择是每个 tenant/course/learner 终身一张证书，撤销后不重发；本次也验证了这个选择，但它不是题目明确规定的唯一方案。

## A5：DST、本地时间与日历日期排序

**要求。** 指定 UTC 时刻在 East 显示 Jan 11 00:30、West 显示 Jan 10 21:30；日期排序和 CSV 使用租户本地日历日期。

**设计。** 保存 UTC issued_at；租户保存 IANA timezone，用 ZoneInfo 转换。详情/列表返回本地年月日时分；发证时另存 issued_local_date，排序和 CSV 使用这个字段。相同日期按证书 ID 升序，即使主排序方向是 desc 也一样，形成确定顺序。

**已验证。** 题目两地精确时间、Sydney 冬季 UTC+10 的固定样例；跨本地午夜样例；同一本地日但时分不同的记录；日期升降序、跨分页顺序、CSV 与列表一致。期望顺序手写为 asc `[4,1,5,3]`、desc `[3,1,5,4]`，不是调用应用排序函数产生答案。Chrome 原实测也看到指定显示值。

**完备性。** 题目给定 DST 样例和“按日而非时间戳”覆盖较强；未覆盖 DST 切换当日重复/跳过的小时、更多时区、时区规则库升级。租户时区在本题中固定；如果将来可修改，动态显示和已存日期可能不一致，需另外设计迁移。这不是当前已实现的配置修改功能。

## A6：十万行导出、稳定排序与并发列表

**要求。** 每次导出 60 秒内完成；只含匹配的 East 数据；排序及相等键次序正确；导出期间列表成功。

**设计。** 生成器要求新数据库路径，产生恰好 100,000 条 East 记录，保留小型 West 数据。列表与 CSV 共用筛选/排序定义，参数绑定，排序字段白名单，末尾追加 ID ASC。CSV 不接受分页限制。单个有序 SELECT 在读事务内固定快照，`fetchmany(1000)` 分批编码 CSV，独立连接，WAL 模式。

同步端点和同步流迭代由已安装的 Starlette 在线程池执行；这点已查看本地依赖源码。分批读取减少应用端同时持有的行数，但 SQL 排序仍可能使用临时存储，不能称为整个系统恒定内存。前端使用 response.blob()，会把完整文件缓存在浏览器内存后下载。

**已验证。** CSV 用解析器处理，不按物理换行数计数；种子包含逗号、引号、换行。用数据库原始记录及独立 Python 排序构造期望，逐字段比较全部匹配行；比较两次完整响应字节；验证 100,000 个唯一 serial 和 West 隔离。过滤 Alex 得 33,299 行，另测不筛选的完整 100,000 行，以及另一个排序字段和降序。本次补测 4 种搜索 × 4 个排序字段 × 2 个方向共 32 组小数据列表/CSV 对齐。

本次真实 HTTP 计时：

| 项目 | 结果 |
| --- | --- |
| 生成 100,000 East 行 | 1.057 秒 |
| 第一次过滤导出，33,299 行 | 0.240 秒 |

**完备性。** 本机题目规模和所测查询已满足 60 秒；不能推导所有机器、所有排序、几十个同时导出都满足。32 组组合是小数据验证，不是 32 组十万行基准。没有内存/RSS 实测，也没测中途断连、导出过程中修改数据、多个导出长期并行。单次读快照保证一次导出内部一致；两个导出之间若数据库改变，不承诺完整字节相同。没有断点续传，题目 A6 本身也未要求。

## A7：撤销重试与审计

**要求。** 首次撤销改变状态并增加一个事件；重复请求不能重复审计。

**设计。** 写事务中先按租户找证书，再执行 `UPDATE ... WHERE status='ACTIVE'`。只有 rowcount 表示实际发生状态变化时才插 REVOKED 审计；状态和审计一起提交。已经撤销时不再写，返回当前详情；首次 revoked_at 不变。`UNIQUE(certificate_id,event_type)` 是额外防线。

因此无需用缓存记录“撤销请求来过”：数据库持久状态决定这次是否真的发生业务事件。其幂等性来自一次性的状态转换；A2 则还要保存整个批量操作的历史结果。

**已验证。** 5 路并发撤销、再顺序重复，全部结果一致；状态 REVOKED，保留原 ISSUED、只增加一个 REVOKED，证书和操作数量不变。注入撤销审计失败后，状态仍 ACTIVE、计数不变。A1 覆盖越权撤销。Chrome 原实测包含取消、确认、状态更新和撤销按钮消失；本次补测重启后重复撤销仍得到同一结果。

**完备性。** 核心状态转换和审计原子性覆盖较强。没有单独模拟“撤销提交成功后丢响应”的网络故障；已验证的重试路径支持这一行为，但不能把推理写成已经实测。锁竞争仍受 A2 提到的 15 秒等待上限约束。

## 对验证完备性的最终评价

不能给出“100% 覆盖”或一个无依据的覆盖率。现有证据强在：真实 HTTP 并发、DB 持久化结果、数据库副作用断言、局部/整体失败注入、独立排序期望，以及浏览器真实网络故障。

明确留白：进程在提交瞬间崩溃、磁盘故障、长时间高并发、跨刷新恢复操作、导出断流与内存测量、时区切换瞬间、其他 OS/浏览器。题目没有要求生产认证、队列或断点续传，不应为这些留白无条件增加功能。

最需要优先对齐的是 A2 的失败协议：现在保证数据库副作用不重复，但长等待者可能得到 503，必须继续使用同 key 重试。如果评估方要求每个等待者都直接拿到同一结果，当前实现存在要求差距。本次仅记录，不在截止时间后修改实现。README 原“没有已知未修复 A1–A7 缺陷”的宽泛说法已补充此限定。
